# 06 质量验证与验收标准

## 1. 为什么质量系统是核心功能

888 的卖点不是“能生成”，而是“知道自己生成得是否可信”。

因此测试体系必须同时验证：

- 软件正确性
- 世界几何正确性
- 视觉一致性
- 证据可追溯性
- 不确定性表达
- 任务可靠性
- 导出完整性

---

## 2. 固定测试集

仓库必须长期保留脱敏或可公开的固定 Test Dataset。

建议至少包含：

### S1 单房间连续多图

- 10～30 张
- 高重叠
- 有尺度参考

验证 SfM / MVS。

### S2 单房间跳跃视角

- 左侧
- 右侧
- 正面
- 低重叠

验证语义空间关联。

### S3 多房间

- 客厅
- 走廊
- 厨房

验证 Zone / Portal。

### S4 室内 + 室外

- 客厅
- 落地窗
- 建筑外立面
- 花园

验证 Indoor / Outdoor 对齐。

### S5 室内外完全无共同视觉区域

验证多假设与不确定性。

### S6 多楼层

验证 Stair / Height。

### S7 单图

验证快速初始化与 Generated 标记。

### S8 视频

验证关键帧与连续相机。

### S9 差素材

- 模糊
- 过曝
- 低分辨率

验证质量降级。

## 4. 集成测试

完整链路：

```text
导入照片
→ Observation
→ Matching
→ Camera
→ Zone
→ Reconstruction
→ Candidate
→ Validation
→ Revision
```

每条主链都必须有固定测试。

---

## 5. 几何指标

在有参考真值的数据集使用：

### Reprojection Error

建议初始门槛：

- Median ≤ 2 px
- P90 ≤ 5 px

具体门槛可按数据集分级。

### 相机位置

有真值：

- 相对轨迹误差
- 旋转误差

### 尺度

存在真实尺度 Anchor 时：

- 关键尺度误差目标 ≤ 5%

无尺度 Anchor：

不得声称米制精度。

### Mesh / Point Cloud

有 Ground Truth 时：

- Chamfer
- Completeness
- Accuracy

---

## 6. 多图匹配指标

必须统计：

- Match Precision
- Match Recall
- False Anchor Merge
- False Entity Merge
- Missed Same Entity

其中 False Merge 的危害高于漏合并。

所以设计上宁可：

> “暂时不知道是不是同一对象”

也不要轻易把两个不同对象合并。

---

## 7. Zone / Portal 指标

对固定场景标注：

- Zone Count
- Zone Membership
- Portal Recall
- Portal Precision
- Indoor / Outdoor Classification
- Floor Assignment

最重要的是拓扑正确性。

例如：

```text
客厅 → 门 → 花园
```

比绝对坐标误差 20cm 更重要。

---

## 8. 假设系统验收

必须专门测试：

### 信息不足

系统保留至少两个合理 Hypothesis。

### 新证据进入

错误 Hypothesis 分数下降。

### 强证据

正确关系被提升为 Verified。

### 证据冲突

不能无声覆盖。

这是 888 与普通生成系统的核心区别，必须作为一级测试对象。

---

## 9. 视觉指标

重渲染验证：

- SSIM
- LPIPS
- Feature Similarity

但不能只优化像素。

必须同时参考：

- Depth
- Silhouette
- Semantic
- Occlusion

否则可能出现“画面很像，但 3D 是错的”。

---

## 10. 自动错误注入

测试 Validator / Repair Planner 时主动制造错误。

例如：

### Transform Fault

- x +0.3m

期待：

- POSITION_ERROR

### Scale Fault

- ×1.2

期待：

- SCALE_ERROR

### Camera Fault

- yaw +5°

期待：

- CAMERA_ERROR

### Wrong Asset

替换成类似但不同椅子。

期待：

- GEOMETRY / SEMANTIC ERROR

自动错误注入应该成为 CI 测试。

---

## 11. Repair 验收

Repair 不只看“执行成功”。

必须验证：

```text
修复前误差
>
修复后误差
```

如果修复恶化：

- 回滚 Candidate
- 降低策略优先级
- 尝试下一种 Repair

---

## 12. 可信度校准

Confidence 要做 Calibration。

例如标成 90% 的关系，在长期测试中应该明显比标成 60% 的稳定。

可以使用：

- Reliability Diagram
- ECE

避免 Confidence 只是模型随便吐出的数字。

---

## 13. Next Best View 验收

在预设缺失观测场景：

1. 隐藏一组关键照片。
2. 让系统推荐下一视角。
3. 从 Ground Truth 照片库中选择最接近推荐视角的照片。
4. 加入。
5. 计算世界不确定性变化。

要求推荐观测平均显著优于随机选择。

---

## 14. 室内外专项验收

### Case A：共享窗

室内和室外都看到同一窗。

期待：

- Anchor Match
- 相对关系收敛

### Case B：共享门

同理。

### Case C：无共享区域

期待：

- 不生成假 Verified
- 建立多个 Hypothesis
- 连接区标为 Generated / Inferred

### Case D：补新照片

新增门口照片。

期待：

- 错误假设被淘汰
- Generated Transition 被真实结构替代
- 历史 Revision 可回看

---

## 15. 软件稳定性

### Crash Recovery

强制结束：

- Desktop
- Core
- Vision Worker

重启后：

- 已提交 Revision 不丢
- Running Job 转 Recoverable / Failed
- 可恢复任务继续

### Provider Failure

模拟：

- 429
- 500
- timeout
- invalid response

不能损坏世界。

### Disk Full

写文件失败时：

- 不提交数据库引用
- 显示明确错误

## 16. 性能测试

场景分级：

### Small

- 50 Observations
- 1 Zone

### Medium

- 500 Observations
- 10 Zones

### Large

- 5000 Observations
- 大型世界

关注：

- 项目打开时间
- UI FPS
- 内存
- SQLite Query
- Viewer Streaming
- Task Queue
- GPU Memory

性能回归进入 CI / Benchmark。

---

## 17. UI 验收

普通用户必须看得懂：

- 哪些区域可信
- 哪些是 AI 补的
- 当前做到了哪一步
- 哪个任务失败
- 为什么需要补拍
- 补拍哪里
- 当前世界可否导出

不能要求用户读日志才能判断状态。

---

## 18. 数据安全

测试：

- 路径穿越
- 恶意文件名
- 超大图片
- 损坏视频
- 损坏 glTF
- Provider 返回危险路径
- Blender Tool 输入

Worker 只能访问项目授权路径。

---

## 19. 导出验收

每种 Compiler Target 都有打开测试。

### GLB

Three.js / glTF validator。

### Blender

自动 headless 打开并检查：

- 对象数
- 缺失纹理
- 相机
- 尺度

### Unity / Godot / Unreal

至少保存一个官方兼容 Fixture 工程用于自动或半自动导入验证。

---

## 20. 回归策略

每修一个真实 Bug：

1. 提取最小 Fixture。
2. 写测试。
3. 修复。
4. 加入长期回归。

不得只修代码不留下验证。

---

## 21. 阶段完成标准

功能只有满足以下条件才叫完成：

```text
代码已实现
+
真实链路已跑通
+
失败路径已测试
+
数据持久化正确
+
UI 可理解
+
回归测试存在
+
没有破坏旧 Fixture
```

---

## 22. 项目级最终验收

888 达到第一阶段完整产品标准时，至少必须通过：

### 场景 1

一组连续室内照片 → 高可信可进入房间。

### 场景 2

多张跳跃照片 → 自动形成正确 Zone 拓扑。

### 场景 3

一张室内 + 一张室外 → 建立统一 World，并显式表达未知连接。

### 场景 4

补充门口照片 → 世界自动重新收敛，低可信补全被真实证据替换。

### 场景 5

人工移动一个对象造成错误 → Validator 检出 → Repair 自动修正。

### 场景 6

系统能够推荐下一张最有价值的照片。

### 场景 7

同一世界成功输出 Web / GLB / Blender。

满足这些条件后，888 才真正从“AI 3D Demo”跨入“证据驱动世界重建系统”。

## 23. AI 驱动开发质量门

AI 主导开发时，质量系统还承担“阻止 AI 把已正确能力改坏”的职责。

### 23.1 每个 PR 的基础质量门

至少包含：

    格式检查
    → 静态分析
    → Schema 兼容检查
    → 架构依赖检查
    → Rust 测试
    → Python 测试
    → TypeScript 测试
    → 数据迁移测试
    → 相关 Fixture 集成测试
    → 回归检查

文档、注释或纯资源变更可以按影响范围裁剪，但不能由 AI 自行声称“无需测试”而跳过。

### 23.2 重型质量门

以下任务可以放入 Nightly、里程碑或 GPU Runner：

- 完整 COLMAP 重建
- Gaussian Splat 训练
- 大型 Mesh 重建
- 全数据集 Validator
- GPU Memory Benchmark
- 大场景性能回归

PR 中至少要运行与改动直接相关的轻量 Fixture。

### 23.3 架构守卫

自动检测并拒绝：
- UI 直接访问 SQLite。
- Worker 直接写正式世界状态。
- Provider 直接写 World State。
- Agent 绕过 Command API。
- Compiler 修改 Canonical World State。
- 未经 Schema 生成器产生的跨语言重复协议。

### 23.4 AI 独立复核

高风险改动至少经过第二次独立 AI Review。

Review 重点：
- 是否违反权威文档。
- 是否遗漏调用链。
- 是否只实现 happy path。
- 是否引入重复状态源。
- 是否修改了不相关模块。
- 是否有 Fixture 覆盖。
- 是否真实闭环。

### 23.5 真实缺陷沉淀

任何真实 Bug 修复都必须：复现 → 最小 Fixture / Test → 修复 → 验证 → 加入长期回归。

禁止仅修当前样例。

### 23.6 AI 完成声明标准

AI 只有在以下内容均有证据时才能声明完成：

- 用户要求全部实现。
- 代码实际存在于目标分支。
- 测试实际运行。
- Fixture 实际通过。
- 数据迁移与持久化实际验证。
- 未发现相关回归。
- 已检查最终 diff / 文件状态。

若受环境限制无法完成某项验证，必须明确标记为“未验证”，不得推断为成功。

## 24. 联想推理专项验收

联想系统必须单独测试，不能只看最终世界是否“看起来合理”。

### 24.1 Proposal Recall

真实关系存在但直接证据不足时，联想是否把正确关系放入 Top-K。

### 24.2 Proposal Precision

联想提出的候选中，有多少具备实际验证价值。

### 24.3 False High-confidence Association

错误联想被打成高分属于高风险回归。

默认应作为 HARD_FAIL 指标。

### 24.4 Evidence Conversion Rate

联想产生的 Proposal 中，有多少最终通过新 Evidence 被验证。

### 24.5 Rejection Correctness

新证据否决联想后：

- Proposal 必须降权或失效。
- 相关 Hypothesis 必须重算。
- 不得残留在 Verified World State。

### 24.6 Zero-overlap Fixture

两张无共同像素照片：

- 允许产生 Weak Proposal。
- 禁止直接产生精确 6DoF。
- 禁止直接 Verified。
- 若没有足够证据，必须保持 Pending / Hypothesis。

### 24.7 联想驱动 Next Best View

对预设歧义世界：

1. 生成多个 Hypothesis。
2. 让联想系统提出验证问题。
3. 推荐下一视角。
4. 加入对应观测。
5. 测量 Hypothesis Entropy / Uncertainty 是否显著下降。

### 24.8 反幻觉回归

必须自动验证：

- ASSOCIATIVE 不升级为 OBSERVED。
- 单一 Proposal 不升级为 VERIFIED。
- 强 Evidence 与 Proposal 冲突时 Evidence 优先。
