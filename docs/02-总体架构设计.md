# 02 总体架构设计

## 1. 架构目标

888 的核心不是某一个生成模型，而是一套长期稳定的世界求解体系。

系统要保证：

- 模型可替换
- Agent 可替换
- 3D 表示可混用
- 输入来源可扩展
- 新证据可以重新求解旧结论
- 每一步可追溯
- 长任务可暂停、恢复、重试
- 局部失败不会摧毁整个工程
- 世界状态与导出平台解耦

因此采用“证据锚定、联想探索、世界状态居中、生成与重建分离、验证闭环”的总体架构。

### 1.1 核心范式：Evidence-grounded Associative World Compiler

888 的长期核心定义为 **Evidence-grounded Associative World Compiler（证据锚定的联想式世界编译器）**：

- Evidence Graph 保存系统实际获得的证据。
- Associative Prior Graph 负责根据视觉、语义、结构、案例和世界常识提出可验证的 Proposal。
- Hypothesis Graph 保留信息不足时的多种世界解释。
- Constraint Solver 负责让世界状态根据新证据持续收敛。
- Reconstruction / Generation 只产生 Candidate。
- Evaluator 负责判断 Candidate 与真实观测是否一致。
- Repair Planner 优先局部调整，无法修复时才重新重建或生成。
- World Compiler 最终把同一份 Canonical World State 编译到不同运行平台。

因此产品运行闭环可以概括为：

```text
证据
↓
联想先验 / Proposal
↓
世界假设
↓
求解
↓
重建 / 生成
↓
验收
↓
修复
↺
↓
世界编译
```

## 3. 交互层

交互层只表达用户意图，不直接控制模型。

入口可以包括：

- 桌面应用
- 浏览器
- CLI
- Agent
- 本地 API

它们最终统一提交 Command。

示例：

```json
{
  "type": "IMPORT_OBSERVATIONS",
  "project_id": "home-001",
  "files": ["IMG_001.jpg", "IMG_002.jpg"]
}
```

或：

```json
{
  "type": "RECONSTRUCT_REGION",
  "zone_id": "living-room",
  "quality": "high"
}
```

这样 Claude、Codex 或其他 Agent 不需要知道底层脚本。

## 4. Observation Engine

所有原始输入先转换成标准 Observation。

### 输入

- Image
- Video
- Depth
- LiDAR
- GPS
- EXIF
- IMU
- User Hint
- Manual Anchor

### 输出

每个 Observation 包含：

- 原始资产引用
- 时间
- 相机内参候选
- 相机位姿候选
- 特征描述
- 深度图
- 分割结果
- 语义对象
- 平面与边缘
- 可识别锚点
- GPS / EXIF
- 质量评分
- 计算来源

Observation 本身不可被后续生成内容覆盖。

---

## 5. Evidence Graph

Evidence Graph 保存系统真正“知道”的事实与证据。

节点例如：

- Observation
- Anchor
- Entity
- Plane
- Zone
- Camera
- Material Candidate

边例如：

- same_object
- visual_match
- attached_to
- inside
- connected_via
- visible_from
- same_plane
- same_building
- temporal_successor
- contradicts

每条关系都包含：

- 来源
- 计算方法
- 权重
- 置信度
- 时间
- 状态
- 可撤销性

---

## 6. Hypothesis Graph

当证据不足时，不直接写死世界状态。

例如：

```text
客厅与外立面的关系：
H1：一层东侧 0.42
H2：一层西侧 0.35
H3：二层东侧 0.18
H4：其他      0.05
```

后续新观测进入后重新评分。

Hypothesis 可以：

- 被强化
- 被削弱
- 被合并
- 被否决
- 被升级为 Verified Relation

这样避免早期错误持续污染后面的世界。

---

## 7. Spatial / Constraint Solver

这是世界收敛的数学核心。

负责：

- 相机位姿
- 世界尺度
- 空间坐标
- 平面关系
- 房间拓扑
- Anchor 对齐
- Zone 关系
- 室内外连接
- 楼层关系

采用两类求解同时工作：

### 几何约束

- Feature reprojection
- Relative pose
- Depth consistency
- Plane constraint
- Known scale
- Gravity direction
- Manhattan world
- GPS
- IMU

### 语义 / 拓扑约束

- 门属于两空间连接
- 窗通常位于外墙
- 楼梯连接不同高度
- 固定柜体附着墙面
- 同一对象不能同时存在于不可能的位置

数学层负责求解，语义层提供约束，不让大模型直接写坐标。

---

## 8. Canonical World State

这是系统唯一正式世界状态。

任何渲染器、生成器、编辑器都只能通过标准接口读写它。

核心对象：

- World
- Zone
- Anchor
- Portal
- Entity
- GeometryRepresentation
- Material
- Camera
- Light
- Audio
- ObservationBinding
- Confidence
- Provenance
- TimelineState

World State 不保存“某模型返回了什么 JSON”这种 Provider 私有数据。

Provider 私有数据进入 Job / Artifact Provenance。

---

## 9. Reconstruction Engine

负责从真实观测恢复内容。

模块化能力：

- 特征提取
- 图像匹配
- SfM
- Bundle Adjustment
- MVS
- 深度融合
- TSDF
- Mesh Reconstruction
- Gaussian Splat
- NeRF
- Texture Projection
- Camera Calibration

所有重建结果都返回标准 Geometry Candidate。

候选通过验证后才能成为正式世界资产。

---

## 10. Generation Engine

生成只负责无法直接重建的内容：

- 遮挡背面
- 缺失房间
- 缺失过渡空间
- 单物体补全
- 材质补全
- 远景
- 音效
- 可选角色

生成器通过 Provider Router 调用。

禁止业务层直接写：

```text
if provider == worldlabs
```

业务层只表达 Capability：

```text
generate_world_completion
generate_object_mesh
generate_texture
generate_audio
```

---

## 11. World Optimizer

World Optimizer 的目标是“尽可能修改现有世界，而不是重新生成”。

修复优先级：

1. Camera pose
2. Entity transform
3. Scale
4. Geometry deformation
5. Material parameter
6. Lighting
7. Texture reprojection
8. Local geometry replacement
9. Provider regeneration

这样降低成本，同时保持跨视角稳定。

---

## 12. Render & Verify

每个正式 Candidate 进入世界前都应验证。

验证视角优先使用真实 Observation 的相机位。

比较：

- Reprojection Error
- Silhouette IoU
- Depth Error
- Normal Consistency
- Color Error
- SSIM
- LPIPS
- Feature Similarity
- Semantic Consistency
- Occlusion Consistency

Evaluator 输出结构化问题：

```json
{
  "entity_id": "table-01",
  "issues": [
    {
      "type": "POSITION_ERROR",
      "axis": "x",
      "estimated_delta_m": -0.21,
      "confidence": 0.91
    }
  ]
}
```

Repair Planner 根据问题类型选择修复策略。

## 13. Task Graph

任务执行必须显式建图。

示例：

```text
导入照片
 ├─ 提取 EXIF
 ├─ 图像质量检测
 ├─ 特征提取
 ├─ 深度估计
 └─ 语义分割
        ↓
图像匹配
        ↓
相机求解
        ↓
世界状态更新
        ↓
局部重建
        ↓
验证
```

每个节点具有：

- 输入
- 输出
- 依赖
- 状态
- 重试策略
- 超时
- Provider
- 资源需求
- 成本
- 缓存键

---

## 14. Job Engine

负责：

- DAG 调度
- CPU / GPU 资源队列
- 并发限制
- 网络任务
- 外部 API
- Retry
- Backoff
- Pause
- Resume
- Cancel
- Checkpoint
- Crash Recovery
- Cost Budget

系统重启后任务可以继续。

不得使用“Agent 还记得做到哪一步”作为恢复机制。

---

## 15. Provider Router

Provider 分为能力，而不是按厂商写业务。

例如：

```text
WORLD_GENERATION
OBJECT_3D
IMAGE_EDIT
DEPTH
SEGMENTATION
AUDIO
TEXTURE
CHARACTER
```

每个 Provider 声明：

- Capability
- 输入类型
- 输出类型
- 价格
- 质量等级
- 时延
- 最大输入
- 可用状态
- 地区 / 授权限制

Router 根据：

- 任务质量目标
- 成本预算
- 延迟
- 用户偏好
- Provider 健康状态

自动选择。

---

## 16. World Compiler

Compiler 只读 Canonical World State。

根据 Target Profile 生成平台资产。

例如移动端：

- LOD 降级
- 纹理压缩
- 合并静态 Mesh
- 简化 Collider
- 远景替换为 Impostor

例如 Blender：

- 保持高精度 Mesh
- 完整材质
- 相机
- 灯光
- Collection

世界本体和编译产物必须分离。

---

## 17. 数据流与依赖规则

严格规则：

1. 原始 Observation 永不被生成资产覆盖。
2. Evidence 只来自可追溯来源。
3. Hypothesis 不能直接升级为事实。
4. Generated 不能自动标为 Verified。
5. Renderer 不修改世界数据。
6. Provider 不直接写 World State。
7. Worker 不直接控制 UI。
8. Agent 不直接操作底层 Provider。
9. Compiler 不反向污染 Canonical World State。
10. 所有变更通过事务和版本记录。

新模型：

```text
实现 Provider Adapter
→ 声明 Capability
→ 注册 Router
```

新重建算法：

```text
实现 Reconstruction Plugin
→ 输出标准 Candidate
```

新平台：

```text
实现 Compiler Target
```

```text
只接 Command API
```

不修改核心世界模型。

## 20. 架构冻结原则

第一版最重要的是冻结以下协议：

- Observation Schema
- Evidence Schema
- Hypothesis Schema
- World State Schema
- Artifact Schema
- Task Schema
- Provider Capability
- Evaluator Result
- Compiler Target

算法可以换，协议不要频繁变。

如果这些协议稳住，未来无论 Gaussian Splat、NeRF、世界模型、生成式 3D 如何更新，888 都只需要替换实现层，而不需要再推翻架构。

## 21. AI 驱动研发架构

当项目主要由 AI 持续推进时，研发架构本身也必须成为系统的一部分。888 增加独立的 **AI Development Control Plane（AI 开发控制层）**，它不进入产品运行时，但负责约束研发过程。

组成：权威文档 + 单一 Schema 真相源 + 机器可执行任务 + 架构依赖守卫 + 固定 Fixture 数据集 + 自动测试 / Benchmark + PR 审计 + 回归闭环。

### 21.1 Monorepo 原则

888 保持单仓库。模块化不等于微服务化，不因为模块变多而拆成多个仓库或大量网络服务。

这样可以保证 AI 在一个上下文内完成影响分析、类型同步、测试修改和原子重构。

### 21.2 固定依赖方向

允许依赖：

    UI
    ↓
    Command API
    ↓
    Core Services / Job Engine
    ↓
    Worker SDK
    ↓
    Python Worker / Tool Worker

    Provider → Candidate
    Canonical World State → Compiler

明确禁止：UI → SQLite、UI → Provider 原始 API、Worker → SQLite、Worker → 正式 World State、Provider → 正式 World State、Agent → Provider 原始 API、Compiler → 反向修改 Canonical World State。

这些边界必须由静态检查或仓库脚本自动验证，不能只写在文档里。

### 21.3 Agent 入口

任何 AI Agent 必须从 `AGENTS.md` 开始，并确认当前任务对应的权威文档、允许修改模块、依赖边界、必须运行的测试和完成标准。

Agent 不得把自己的上下文记忆视为项目状态真相。

### 21.4 Schema 单一真相源

当前固定为：

    packages/schema
          ↓
    JSON Schema Draft 2020-12 唯一权威 Schema
          ↓
    自动生成 Rust / TypeScript / Python 类型

任何语言都禁止手工维护第二套同义结构。

### 21.5 AI 任务必须可机器验收

任务必须尽量包含输入 Fixture、期望输出、允许修改范围、必须通过的测试、性能或质量门槛、禁止回归项。

例如“完善多图导入”不是合格任务；“10 张图片中 2 张重复，导入后 Observation=10、Physical Asset=8，重启后状态一致”才是可执行任务。

## 21.6 联想推理引擎边界

新增逻辑模块：

    Evidence Graph
          ↓
    Associative Engine
          ↓
    Associative Prior Graph
          ↓
    Hypothesis Graph
          ↓
    Constraint Solver

Associative Engine 可以调用视觉检索、结构规则、Case Retrieval、VLM / LLM，但输出必须是结构化 Proposal。

硬边界：

- Proposal 不直接写 Canonical World State。
- Proposal 不创建 Observed / Verified。
- Proposal 不单独创建绝对尺度或精确 6DoF。
- Proposal 与强 Evidence 冲突时必须降权或失效。
- Proposal 进入 Hypothesis 后仍需 Solver / Validator / 新证据验证。

详细规则见 `docs/17-联想推理与先验系统设计.md`。

## 21.7 AI 运行时兼容层

不同 AI 的 Prompt 偏好、Tool Calling、结构化输出、置信度表达和创意能力存在天然差异。888 不要求模型内部行为一致，而统一它们的对外行为合同。

新增：

    Canonical Capability Contract
              ↓
         Provider Router
              ↓
      AI Compatibility Layer
      ├─ Model Registry
      ├─ Behavior Profile
      ├─ Prompt Compiler
      ├─ Tool Adapter
      ├─ Output Normalizer
      ├─ Validator Chain
      ├─ Confidence Calibrator
      └─ Creativity Controller
              ↓
        各类 AI / VLM / LLM

上层业务只看到统一 Capability Request 与标准 Candidate / Proposal。

### 严谨与创意双通道

AI 任务分成：

- **Factual Channel**：低自由度、强 Schema、强 Evidence 引用，用于事实抽取、工具调用和可验证判断。
- **Exploratory Channel**：允许多样化候选、联想和创意补全，但只能产出 Proposal / Hypothesis / Candidate。

无论创意档位多高，进入 Canonical World State 的证据与 Validation 门槛保持不变。

详细规范见 `docs/18-AI运行时兼容与行为标准.md`。
