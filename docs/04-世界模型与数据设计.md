# 04 世界模型与数据设计

## 1. 设计目标

世界数据必须做到：

- 可追溯
- 可版本化
- 可重新求解
- 支持不确定性
- 支持多个候选假设
- 支持混合 3D 表示
- 支持后续时间维度
- 与 Provider 解耦
- 与渲染器解耦

SQLite 保存结构化状态，文件系统保存大体积资产。

---

## 2. 核心实体

### World

代表一个长期存在的世界工程。

关键字段：

- id
- name
- schema_version
- created_at
- updated_at
- active_revision
- coordinate_system
- unit

世界默认单位统一为米。

---

### Observation

代表一次真实或用户提供的观测。

类型：

- IMAGE
- VIDEO_FRAME
- DEPTH
- LIDAR
- GPS
- IMU
- USER_HINT
- MANUAL_MEASUREMENT

核心：

- asset_id
- timestamp
- source_type
- camera_intrinsics
- camera_pose_candidate
- quality
- immutable

Observation 不允许生成模型伪造。

---

### Zone

逻辑空间区域。

类型示例：

- ROOM
- CORRIDOR
- FLOOR
- BUILDING
- OUTDOOR
- GARDEN
- STREET
- UNKNOWN

Zone 有自己的局部坐标。

Zone 之间使用关系和 Portal 连接。

---

### Anchor

跨视角 / 跨 Zone 的稳定空间锚点。

例如：

- door-01
- window-03
- facade-corner-01
- fixed-cabinet-02

Anchor 可以存在多个 Pose Candidate。

---

### Portal

连接两个 Zone。

字段：

- from_zone
- to_zone
- anchor_id
- transform
- passable
- confidence

一个 Portal 不一定必须是门，也可以是开放连接。

---

### Entity

世界中的独立对象。

例如：

- sofa-01
- dining-table-01
- tree-03

核心字段：

- semantic_class
- display_name
- zone_id
- transform
- scale
- physical_properties
- lifecycle

---

### GeometryRepresentation

一个 Entity / Zone 可以同时拥有多个几何表示：

- MESH
- SPLAT
- NERF
- POINT_CLOUD
- PRIMITIVE
- BILLBOARD
- COLLIDER

每个表示具有：

- artifact_id
- quality
- source
- valid_region
- lod_level
- verification_state

Canonical World 不把“一个对象只能对应一个 GLB”写死。

---

### Material

独立于 Mesh。

记录：

- base_color
- texture artifacts
- roughness
- metallic
- normal
- emissive
- provenance

---

### Camera

相机状态分：

- observed camera
- optimized camera
- virtual camera

Observed Camera 保留原始参数。

Optimized Camera 是求解结果。

---

## 3. Evidence

Evidence 是最核心的数据类型之一。

示例：

```json
{
  "id": "ev-123",
  "type": "VISUAL_MATCH",
  "subject": "anchor-window-01",
  "object": "observation-002",
  "source_job": "job-998",
  "weight": 0.94,
  "payload": {},
  "created_at": "..."
}
```

Evidence 不能只保存最终结论。

必须保留依据。

---

## 4. Hypothesis

Hypothesis 表示尚未被确认的世界解释。

例如：

```json
{
  "id": "hyp-01",
  "type": "ZONE_RELATION",
  "alternatives": [
    {
      "relation": "living-room->east-side-floor-1",
      "score": 0.42
    },
    {
      "relation": "living-room->west-side-floor-1",
      "score": 0.35
    }
  ]
}
```

状态：

- ACTIVE
- VERIFIED
- REJECTED
- SUPERSEDED

---

## 5. Confidence

Confidence 不等于 Probability 字段到处乱写。

统一使用：

- score
- uncertainty
- evidence_count
- source_quality
- solver_residual

并区分：

- observation confidence
- relation confidence
- geometry confidence
- material confidence

---

## 6. Provenance

任何派生数据必须知道从哪里来。

Provenance 至少记录：

- source observations
- source artifacts
- source entities
- job id
- provider
- model / algorithm
- parameters
- code version
- created_at

这样未来才能：

- 重算
- 比较
- 审计
- 删除某 Provider 生成内容
- 判断哪些结果已过时

---

## 7. Artifact

所有文件统一进入 Artifact Registry。

字段：

- id
- content_hash
- mime
- bytes
- storage_path
- logical_type
- source
- created_at

logical_type：

- ORIGINAL_IMAGE
- PREVIEW
- DEPTH_MAP
- MASK
- FEATURE
- POINT_CLOUD
- MESH
- SPLAT
- NERF
- TEXTURE
- AUDIO
- EXPORT

---

## 8. Revision

用户或系统每次正式改变世界状态时创建 Revision。

Revision 记录：

- parent_revision
- command
- changeset
- actor
- created_at

不要求每个临时优化迭代都形成用户可见 Revision。

只有 Commit World State 时进入历史。

---

## 9. Candidate 与正式状态

重建 / 生成结果先进入 Candidate。

```text
Worker Output
   ↓
Candidate
   ↓
Validation
   ↓
Accepted / Rejected
   ↓
World Revision
```

Provider 不得直接覆盖当前正式资产。

---

## 10. 数据库建议表

第一版可包含：

- worlds
- revisions
- observations
- assets
- zones
- anchors
- portals
- entities
- entity_states
- geometry_representations
- materials
- cameras
- evidence
- hypotheses
- constraints
- candidates
- validations
- jobs
- job_dependencies
- provider_runs
- exports

不要一开始过度拆分，但这些概念边界必须保留。

---

## 11. 坐标体系

### 世界坐标

- 右手坐标
- Y-up 或 Z-up 必须项目级固定
- 单位：米

建议内部采用 Y-up，与 Three.js 友好。

Compiler 负责转成 Unreal / Blender 等目标坐标。

### Zone Local

每个 Zone 可保留局部坐标。

Global Solver 给出：

```text
T_world_zone
```

Entity：

```text
T_world_entity =
T_world_zone × T_zone_entity
```

便于独立优化 Zone。

---

## 12. 尺度

尺度来源标记：

- METRIC_SENSOR
- KNOWN_OBJECT
- USER_MEASUREMENT
- MULTIVIEW_ESTIMATE
- MONOCULAR_ESTIMATE

不允许单目深度自动冒充真实米制尺度。

---

## 13. 关系类型

关系建议统一 Registry：

- INSIDE
- CONNECTED_TO
- ATTACHED_TO
- SAME_AS
- PART_OF
- ABOVE
- BELOW
- NEAR
- VISIBLE_FROM
- OCCLUDES
- SUPPORTS
- SAME_PLANE
- TEMPORAL_SUCCESSOR

业务层不要随意发明字符串。

---

## 14. 时间设计预留

Entity 使用 identity + state。

例如：

```text
entity: sofa-01
  ├─ state@2026-01
  └─ state@2026-05
```

Observation 带 timestamp。

第一版只使用 latest state。

未来再开放时间轴。

---

## 15. 冲突处理

新 Evidence 与旧世界冲突时：

1. 不直接覆盖。
2. 创建 Conflict。
3. Solver 重新计算。
4. 评估是否：
   - Camera 错
   - Anchor 关联错
   - Entity identity 错
   - 时间变化
5. 如果无法自动消歧，提示用户。

---

## 16. 删除策略

删除一个 Observation 时：

- 原图可移出项目引用。
- 查找所有 Provenance 依赖。
- 标记相关 Evidence 失效。
- 触发世界重新求解。
- 不立即物理删除仍被历史 Revision 引用的 Asset。

使用垃圾回收统一清理无引用内容。

---

## 17. 内容寻址存储

物理文件名不承担业务语义。

```text
store/ab/abcdef...
```

“living-room-depth.exr”只是逻辑显示名。

好处：

- 去重
- 安全移动
- 历史共享
- 缓存复用

---

## 18. Schema Version

任何持久化结构必须包含 schema version。

迁移由 Core 执行。

不允许 Python Worker 自己迁移数据库。

---

## 19. 快照

大型项目启动时不应重放所有历史。

周期性生成 World Snapshot：

- 当前 Zone
- Entity
- Geometry refs
- Solver state

Revision 仍然保存增量历史。

---

## 20. 数据一致性原则

必须保证：

1. 数据库事务成功后再发布 UI 更新。
2. 文件先写临时路径，Hash 校验后原子移动。
3. Asset 写成功但事务失败时进入 orphan GC。
4. Job 完成不等于 Candidate 被接受。
5. Candidate 接受必须形成 Revision。
6. UI 本地临时编辑可以未提交，但关闭前必须明确保存或放弃。

这套数据设计是整个 888 可以长期升级而不推翻工程的基础。
